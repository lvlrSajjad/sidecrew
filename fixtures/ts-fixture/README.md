# ts-fixture

The TypeScript half of the verifier's ground truth: 21 small pure functions with known behaviour, plus
eight tests that all compile and all pass, four of which mean nothing.

It is a separate npm project on purpose — `sidecrew doctor` and the verifier probe the toolchain of the
project they are pointed at, and this is the project they will be pointed at. Nothing here is installed
by the root package and none of it is published. **`npm i` in this directory** before running the slow
tests or `npm run measure:verifier-ts` from the repo root.

```
src/          strings · numbers · arrays · machine · async — 21 functions, one of them wrong on purpose
test/         empty, and stays empty: the verifier puts exactly one candidate here, in a sandbox copy
legitimate/   four candidates that survive the whole pipeline, one per shape
tautological/ four that compile, pass, and say nothing
candidates.json  the catalogue both the slow test and the cost script read
stryker.config.mjs  generated by src/verifier/ts.ts; a unit test fails if the two drift apart
```

`legitimate/` and `tautological/` sit one directory deep, like `test/`, so a candidate's
`import … from "../src/…"` is the same wherever it is read from. They are type-checked but not run by
`npm test` here — `vitest.config.ts` collects `test/**` only, and these are inputs to a detector.

## The planted bug

`truncate(text, maxLength)` is documented to return text that already fits **unchanged**. It does not:

```ts
if (text.length < maxLength) return text;   // should be <=
```

so `truncate("abcd", 4)` returns `"abc…"` instead of `"abcd"`. It is wrong on exactly one input class —
text whose length is the limit — and the result still has the right length, so nothing that checks
`result.length <= maxLength` will notice. Only a boundary test that asserts the exact value will.

This is the fixture's most useful property, and it is ground truth for two things at once:

1. a boundary test asserting the **correct** answer fails the pass stage, because the source is wrong;
2. a boundary test asserting `"abc…"` **survives with a perfect score** — it kills every mutant and
   encodes the bug. That is ADR-0006's snapshot-of-current-bug, reproducible on demand, and the reason
   survival is a filter rather than an endorsement.

Both are asserted in `test/verifier-ts.slow.test.ts`. Nothing in this directory tests `truncate`'s
boundary, so the fixture's own suite stays green — and the bug is documented here rather than in the
source, because a worker model reads the source.

## Module resolution

`tsconfig.json` uses `moduleResolution: "Bundler"` rather than `NodeNext`, and that is a measurement
decision. Under NodeNext every relative import needs a `.js` extension; a worker model that omits one
fails the compile stage for a convention nobody told it about, and the discard rate would then be
reporting on our tsconfig instead of on the model. Vitest resolves through Vite, so Bundler is also what
actually runs. A project that does use NodeNext needs the extension in `TestPlan`'s `imports_hint` —
that field exists for exactly this.
