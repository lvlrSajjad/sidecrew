# swift-fixture

The Swift half of the verifier's ground truth: 21 small pure functions with known behaviour, plus nine
tests that all compile and all pass, five of which mean nothing.

It mirrors `fixtures/ts-fixture` function for function, so a difference between the two verifiers is a
difference in the *toolchain* rather than in what they were pointed at. Foundation only — no UIKit, no
network, no clock — and **no simulator**: it is a macOS SwiftPM package, so `swift test` runs it
directly and nothing ever boots a device.

```
Sources/SwiftFixture/  Strings · Numbers · Arrays · Machine · Async — 21 functions, one wrong on purpose
Tests/SwiftFixtureXCTests/   the package's own XCTest suite
Tests/SwiftFixtureTests/     the package's own Swift Testing suite
legitimate/            four candidates that survive the whole pipeline, one per shape, two per framework
tautological/          five that compile, pass, and say nothing
candidates.json        the catalogue the slow test and the cost script both read
muter.conf.yml         generated by src/verifier/swift.ts; a unit test fails if the two drift apart
sidecrew-test.sh       the same, and the more interesting of the two — see ADR-0005
```

`legitimate/` and `tautological/` sit outside `Sources/` and `Tests/`, so SwiftPM never compiles them
as part of the package: they are inputs to a detector, not a suite. The verifier copies exactly one of
them into a test target in a sandbox.

## Two test targets, and why they are not decoration

| target | framework | why both |
|---|---|---|
| `SwiftFixtureXCTests` | XCTest | what most existing Swift packages still use |
| `SwiftFixtureTests` | Swift Testing | what new ones use, and where Muter's kill detection was broken |

Muter 16 decides a mutant was killed by matching `with ([1-9][0-9]*) failure` against the test output.
That is XCTest's summary line. Swift Testing prints `✘ Test run with N tests … failed` instead, which
matches nothing — so before ADR-0005 **every** Swift Testing kill was reported as a runtime error, and
no `@Test` candidate could ever have survived. Keeping both targets here is what made that visible
rather than a thing we shipped. `sidecrew-test.sh` is the fix, and the fixture is where it is checked.

Run the whole thing by hand with `swift test`. Mutate one file with:

```
muter run --files-to-mutate Sources/SwiftFixture/Strings.swift --format json --output report.json
```

`muter.conf.yml` and `sidecrew-test.sh` are checked in so that command sees exactly what the verifier
sees. `SWIFT_TREAT_WARNINGS_AS_ERRORS=NO` is set by the verifier and is worth setting by hand too.

**Muter leaves things behind.** It copies the package to a sibling `swift-fixture_mutated/` directory
and writes `muter_logs/`, and it cleans up neither. The verifier removes both; a run by hand does not.

## 21 functions, 15 of them survivable

`plans/` covers **10 functions in 18 function x shape tasks**, across five modules. The other eleven are
five exemplar hosts and six functions no test can survive, and the split is measured rather than judged —
`experiments/mutant-probe/results/swift-*.json`, one throwaway test per function through the real
verifier:

| | |
|---|---|
| demonstrably survivable | **15** — a mutant was killed by an assertion |
| no mutants at all | 2 — `titleCase`, `unique` |
| every mutant crashes rather than failing an assertion | 3 — `gcd`, `rotate`, `nextState` |
| mutants survived the probe, killability unknown | 1 — `roundTo` |

The middle row is Swift's own failure mode and TypeScript has none of it. `killed` counts only mutants a
test reported a *failure* against; one that crashes the process lands in `timeout`, counts towards the
score and never towards survival (ADR-0005). Muter's `SwapTernary` on `nextState` force-unwraps nil, so
its single mutant can only ever crash — the function has a mutant and no test can survive it.

And nine of the fifteen have **exactly one** mutant, so `killed >= 1` is a demand for a perfect score.
On the TypeScript fixture the median is about eight and killing any one of them is enough. The same rule
is a harder gate here, which is ADR-0018 and is why the two fixtures' survival rates are never averaged.

The explicit loops in `Strings.swift` are already a concession to this (ADR-0005) and were not enough.

## Both frameworks are exercised

`Strings`, `Numbers` and `Arrays` plan XCTest into `SwiftFixtureXCTests`; `Machine` and `Async` plan
Swift Testing into `SwiftFixtureTests`. That is deliberate: ADR-0005's kill-attribution wrapper is the
most expensive thing in the Swift verifier, and a plan set that never used Swift Testing would leave it
unexercised end to end. The framework is held constant per task across configurations, so it does not
confound a comparison between workers.

## The planted bug

Documented **here and not in the source**, for the same reason the TypeScript fixture does it: a worker
model reads the source. `Strings.swift` said so in `truncate`'s own doc comment until Phase 5 noticed
that `line_range` starts at the doc comment, so the comment reaches the worker in
`WorkerTask.function.source` — which would have handed a Swift worker the answer to the one input class
the fixture exists to catch, while the TypeScript worker got nothing. Two fixtures being compared cannot
differ in what they tell the model.


`truncate(_:maxLength:)` is documented to return text that already fits **unchanged**. It does not:

```swift
if text.count < maxLength { return text }   // should be <=
```

so `truncate("abcd", maxLength: 4)` returns `"abc…"` instead of `"abcd"`. It is wrong on exactly one
input class — text whose length is the limit — and the result still has the right length, so nothing
that checks `result.count <= maxLength` will notice. Only a boundary test asserting the exact value
will.

This is the fixture's most useful property, and it is ground truth for two things at once:

1. a boundary test asserting the **correct** answer fails the pass stage, because the source is wrong;
2. a boundary test asserting `"abc…"` **survives**, killing mutants and encoding the bug. That is
   ADR-0006's snapshot-of-current-bug, reproducible on demand, and the reason survival is a filter
   rather than an endorsement.

Both are asserted in `test/verifier-swift.slow.test.ts`. Nothing in `Tests/` tests `truncate`'s
boundary, so the fixture's own suite stays green — and the bug is documented here rather than in the
source, because a worker model reads the source.

## Why the functions are written with loops

`slugify` could be four chained `replacingOccurrences(of:with:)` calls and `unique` could be
`Array(Set(xs))`. They are not, and that is a measurement decision rather than a style one.

Muter has **four** operators — `RelationalOperatorReplacement`, `RemoveSideEffects`,
`ChangeLogicalConnector`, `SwapTernary` — against StrykerJS's several dozen. A function built out of
Foundation calls with no branches has no mutants at all, and a function with no mutants makes
`killed ≥ 1` unreachable for a reason that has nothing to do with the test. A fixture written in the
most idiomatic Swift would therefore have measured Muter's operator set rather than the verifier.

The gap is real and is not hidden: `Arrays.unique` is still written with a `Set` and a loop that Muter
cannot mutate, and `test/verifier-swift.slow.test.ts` verifies that a perfectly good test of it comes
back with `killed: 0` and an error that says *why* — "muter generated no mutants … this is not a fault
in the test" — so the single retry is not spent rewriting a test that was never the problem.
